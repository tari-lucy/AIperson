# NetTyan — Глубокий анализ проекта (март 2026)

> 159 Python-файлов, ~25K строк, 437 коммитов за 1.5 года.
> Старый пайплайн: 10K строк в 5 файлах, 100 подписчиков за полгода стримов.
> Новый пайплайн: ни разу не выкатывался.

---

## TL;DR

Новый пайплайн **архитектурно лучше** старого на порядок. Но проблема роста канала — не в архитектуре. 100 подписчиков за полгода — это не баг кода, это баг продукта. Пайплайн решает задачу "как технически стримить", но не решает задачу "почему это интересно смотреть". Новый код не изменит эту ситуацию, если не добавить то, чего не хватает на уровне контента и геймплея.

## Что проекту КАРДИНАЛЬНО не хватает

### Уровень "без этого не взлетит"

| # | Проблема | Суть | Сложность фикса |
|---|---------|------|-----------------|
| 1 | **Нет геймплейного интеллекта** | Baritone — это pathfinding, не gameplay. Бот не строит, не принимает решений, не реагирует на ситуации. Зритель видит NPC, а не игрока. | **Очень высокая** — нужна отдельная система принятия игровых решений поверх Baritone |
| 2 | **Нет зрения** | Vision tools = WIP. Бот не видит, что происходит на экране. Не может комментировать, реагировать на визуальные события. | **Средняя** — API для vision есть (screenshot + VLM), нужна интеграция в agent loop |
| 3 | **Нет контент-стратегии** | Система не понимает, что "интересно". Нет генерации моментов, нет нарратива, нет клипов. Стрим — это бесконечный поток однообразных реакций на чат. | **Высокая** — нужен "режиссёр" поверх агента |
| 4 | **Нет памяти и развития персонажа** | Персонаж статичен — это промпт. Нет арки, нет роста, нет "историй". Зритель не видит прогресса. | **Средняя** — нужна система долгосрочной памяти + personality drift |
| 5 | **Нет social media presence** | Ноль автоматических клипов, ноль постов в Twitter/TikTok. В 2026 без этого канал не растёт. | **Средняя** — API для клиппинга и постинга доступны |

### Уровень "мешает, но не критично"

| # | Проблема | Суть | Сложность |
|---|---------|------|-----------|
| 6 | **Operational complexity** | 6+ сервисов, 6+ портов, 4+ API ключа. Запустить на чистой машине — квест. | Средняя — Docker Compose уже есть, нужна документация + health checks |
| 7 | **Нет тестов в CI** | Black + isort, но ни одного pytest. Рефакторинг на удачу. | Низкая — писать тесты для critical path |
| 8 | **Нет продакшн-деплоя** | Проект ни разу не запускался "по-настоящему". Неизвестные баги в продакшне. | Средняя — нужен прогон end-to-end |
| 9 | **4 типа агентов** | CoreAgent, ReactionAgent, ChatAgent, MultiAgent — 4 парадигмы для одной задачи. Путаница. | Средняя — консолидировать в ChatAgent + убрать legacy |
| 10 | **Startup time** | Были фиксы 21с и 43с стартапа БД. Стартовать стрим — долго. | Низкая — уже частично пофикшено |

## Ответ на главный вопрос

### "У нового пайплайна больше шансов, чем у старого?"

**Да, но с оговоркой.**

Новый пайплайн — это хороший **фундамент**. Модульность, Redis, LiteLLM, tool system — всё это позволяет быстро добавлять фичи. Старый монолит на 10K строк в 5 файлах не позволял этого физически.

Но **фундамент ≠ продукт**. Проект сейчас — это инфраструктура для стриминга, а не стример. Как автомобильный завод без дизайнера: может собрать машину, но не знает, какую машину хотят покупать.

### "Будет ли интересен кому-то такой проект?"

**Рынок AI-стримеров в 2026 — конкурентный.** Neuro-sama задала стандарт. Десятки клонов появились и умерли. Чтобы выделиться:

- **Нужен уникальный характер** — не "generic anime girl plays Minecraft"
- **Нужен gameplay** — зритель должен видеть, что бот ИГРАЕТ, а не ходит по прямой
- **Нужна непредсказуемость** — каждый стрим должен быть разным
- **Нужен social media** — без TikTok/YouTube Shorts канал не растёт

### "Что делать?"

**Приоритеты (в порядке impact/effort):**

1. **Game Vision Loop** → бот начинает "видеть" (2-3 дня, максимальный impact)
2. **Commentary Mode** → бот комментирует игру без чата (2-3 дня после vision)
3. **Gameplay Decision Engine** → бот ставит себе цели и выполняет их (1-2 недели)
4. **Long-term Memory** → бот помнит зрителей (3-5 дней, инфра есть)
5. **Auto-clip + Social** → автоматический контент для соцсетей (1 неделя)
6. **Убрать legacy агентов** → оставить ChatAgent, удалить остальное (1-2 дня)
7. **Написать базовые тесты** → не ломать при рефакторинге (2-3 дня)

## Стратегия роста: "бот идёт к людям"

Главный сдвиг в мышлении: **не ждать зрителей на стриме, а идти туда где уже есть люди.** Контент рождается из диалогов с живыми людьми, не из соло-геймплея.

### Идея 1: Nekto.me голосовая рулетка

Бот заходит в голосовую рулетку и общается с рандомными людьми.

**Почему это может сработать:**
- Бесконечный поток живых собеседников — не нужна своя аудитория
- Каждый разговор — потенциальный клип
- Реакции людей на AI = контент сам по себе
- TTS + эмоции уже работают

**Техническая реализация:**
- Аудио I/O: виртуальный микрофон (VB-Cable / VoiceMeeter) для TTS → Nekto
- Захват аудио собеседника → STT (speech_processor.py уже есть)
- Автоматизация UI: pyautogui для "Next" / "Skip"
- Новые тулы: `nekto_next()`, `nekto_skip()`

**Сложность:** Средняя. STT pipeline существует. Основной challenge — стабильность аудио-роутинга и задержка (TTS + LLM latency = 3-5 секунд, это заметно в живом разговоре).

**Потенциальные баги:** 4-6
- Аудио loop (бот слышит сам себя)
- Latency делает диалог неестественным
- Nekto.me может банить за ботов
- STT ошибки на шумном аудио
- Определение "собеседник говорит" vs тишина

**Оценка контент-потенциала: 9/10** — реакции живых людей на AI-собеседника вирусятся.

### Идея 2: Чат-рулетка (видео)

**Статус:** Пока нереализуемо. Требует:
- Рендеринг Live2D аватара в виртуальную камеру (OBS Virtual Camera может)
- Остальное аналогично Nekto.me

**Сложность:** Средняя-высокая. OBS Virtual Camera + аудио роутинг одновременно.
**Отложить** до тех пор пока не обкатается аудио-рулетка.

### Идея 3: Telegram бот в "Дай Винчик"

Бот общается с реальными людьми в приложении знакомств через Telegram user-account.

**Почему это может сработать:**
- Текстовый формат — нет проблем с latency (в отличие от голоса)
- LLM в своей стихии: флирт, юмор, диалог
- NSFW-фильтр показывает фото на стриме только если цензурное — сам процесс фильтрации = контент
- Каждый диалог уникален

**Техническая реализация:**
- Telegram user-account: Telethon / Pyrogram (не bot API — нужен именно user account)
- Новый data_collector: `tg_dating_collector.py` по аналогии с social_service.py
- NSFW-фильтр для фото: VLM с промптом "is this image safe for stream?" или специализированный классификатор (NudeNet, NSFW Detection API)
- Vision тут НУЖЕН — описать фото собеседника для контекста бота
- Тулы: `tg_send(message)`, `tg_like()`, `tg_skip()`, `tg_send_photo()`

**Сложность:** Средняя.
- Telethon интеграция — стандартная, хорошо документирована
- NSFW классификатор — готовые модели есть
- Основная работа — новый data_collector + 3-4 тула

**Потенциальные баги:** 5-7
- Telegram бан user-account за автоматизацию
- NSFW фильтр false positives/negatives
- "Дай Винчик" может иметь свою защиту от ботов
- Скорость ответа (LLM latency нормальна для текста, но dating-приложения ожидают быстрые ответы)
- Определение что собеседник ушёл / перестал писать

**Оценка контент-потенциала: 8/10** — dating AI = кликбейт-заголовок сам по себе. "AI пошла на свидание" — готовый YouTube title.

### Идея 4: Мульти-агент рейды (университетский курс)

Несколько AI VTuber-ов на базе пайплайна заходят на MC сервер одновременно.

**Почему это может сработать:**
- Масштаб: не 1 бот, а 5-10 — это событие
- Каждый бот с уникальной личностью → взаимодействие между ботами = контент
- Университетский курс = команда разработчиков, не один человек

**Проблема из прошлого опыта:** забанили за спам.

**Решение — централизованный координатор:**

```
RaidCoordinator (новый сервис)
├── Очередь сообщений: бот хочет сказать → кладёт в очередь
├── Rate limiter: 1 сообщение на сервер каждые 3-5 секунд
├── Round-robin: боты говорят по очереди
├── Приоритеты: ответ на прямое обращение > случайный комментарий
└── Общий Redis: все боты видят общий ctx_chat
```

**Техническая реализация:**
- Redis уже есть и поддерживает multi-instance
- Новый сервис: `raid_coordinator.py` — очередь + rate limiter + round-robin
- Каждый бот подключается к общему Redis, но отправка чата идёт через координатор
- Конфиг: `raid_config.yml` — задержка между сообщениями, макс. ботов, сервер

**Сложность:** Средняя.
- Redis multi-instance уже архитектурно поддерживается
- Rate limiter — тривиально
- Основная работа — координация "кто сейчас говорит"

**Потенциальные баги:** 4-6
- Race condition при одновременной отправке
- Боты отвечают друг другу бесконечно (loop detection нужен)
- Разные сервера с разными rate limit'ами
- Синхронизация состояния при дисконнекте одного бота

**Оценка контент-потенциала: 7/10** — зависит от исполнения. "Армия AI захватывает сервер" — вирусный потенциал есть, но одноразовый.

### Идея 5: Реакции нейростримерши на видео

Бот смотрит YouTube-видео и комментирует/реагирует в реальном времени. "Content on nothing" — не нужен геймплей, не нужны собеседники, нужен только видеопоток и сильная VLM.

**Почему это может сработать:**
- Реакции — проверенный формат, один из самых популярных на YouTube
- Не нужна аудитория для записи (но нужна для стрима)
- Бесконечный пул контента — любое видео = материал
- AI-реакции = уникальный формат, почти никто не делает
- Эмоциональный TTS + Live2D = зритель видит "живую" реакцию

**Техническая реализация — пайплайн "видеопонимания":**

```
Video Input (YouTube / локальный файл)
  ↓
Frame Sampler (каждые 2-5 секунд или по сцене)
  ↓
Audio Track → STT (что говорят в видео)
  ↓
[Frame + Audio transcript + Previous context]
  ↓
Video-Understanding VLM (GPT-4o / Gemini 2.5 Flash / etc.)
  Промпт: "Ты смотришь видео. Вот кадр и что говорят. Прокомментируй."
  ↓
ChatAgent (реакция: speak + эмоция)
  ↓
TTS + Live2D (озвучка реакции с эмоцией на аватаре)
```

Ключевые компоненты:

1. **Frame Sampler** — не каждый кадр, а по изменению сцены (scene detection) или фиксированный интервал. OpenCV `absdiff()` между кадрами для определения смены сцены.

2. **Audio STT** — субтитры видео через Whisper или YouTube auto-captions API. Даёт контекст что говорят, не только что показывают.

3. **Video-Understanding VLM** — критично выбрать модель:
   - GPT-4o: хорошо понимает видео, дорого
   - Gemini 2.5 Flash: длинный контекст, можно скормить много кадров, дешевле
   - Локальная VLM: медленнее но бесплатно
   - Нужна модель, понимающая мемы, юмор, культурный контекст

4. **Reaction Timing** — бот не должен молчать 30 секунд и потом выдать стену текста. Нужен баланс: короткие реплики часто vs длинный комментарий на ключевых моментах.

**Сложность:** Средняя-высокая. Основной challenge — timing реакций и quality VLM-описаний. Frame sampling + STT — стандартные задачи. Но сделать так, чтобы реакции были "в тему" и вовремя — это prompt engineering + подбор модели.

**Потенциальные баги:** 6-8
- VLM не понимает контекст видео (описывает пиксели, а не смысл)
- Timing: реакция приходит с задержкой 5-10 секунд после момента
- Стоимость API: continuous VLM calls на каждые 3 секунды = дорого
- STT ошибки на музыке/шуме
- Бот повторяет одну и ту же реакцию ("ого", "вау", "интересно")
- Scene detection false positives (быстрый монтаж = слишком много кадров)
- Copyright контента на стриме
- Синхронизация аудио видео с реакцией бота

**Оценка контент-потенциала: 8/10** — "AI смотрит [популярное видео] и офигевает" — готовый шортс. Формат масштабируется бесконечно. Но quality зависит от VLM — если реакции тупые, контент мёртвый.

**Важно:** это не просто "прикрутить VLM". Это полноценный видео-пайплайн с синхронизацией. Зато он переиспользуется: тот же пайплайн работает для VN mode, для чат-рулетки с видео, для любого визуального контента.
